### The NixOS "cannot pip install" constraint is surmountable

This matters directly for post-publish verification. A stock venv install **does** work on this
host; the only blocker is that `z3-solver`'s bundled `libz3.so` cannot find `libstdc++.so.6`:

```
$ ldd .../site-packages/z3/lib/libz3.so
	libstdc++.so.6 => not found
```

Supplying it makes the whole golden path work:

```bash
python3 -m venv testvenv
PIP_USER=0 ./testvenv/bin/pip install model-checker      # PIP_USER=0 required: pip.conf sets install.user=true
LD_LIBRARY_PATH=$(nix eval --raw nixpkgs#stdenv.cc.cc.lib)/lib \
  ./testvenv/bin/model-checker project_demo_logos/examples.py
```

This is a **repeatable recipe for verifying a real PyPI install on NixOS** and should be
captured in the installation docs, which currently say only "Do not use pip installation."

Incidental positive finding: pip resolved **z3-solver 5.0.0.0** (a major version beyond the
`>=4.8.0` floor the project has ever tested), and all four theories ran clean under it. No upper
pin is needed today.

## Critical Issues

### 1. Release evidence no longer matches the tree

**File**: `specs/archive/125_release_engineering_and_pypi_rehearsal/PUBLISH-CHECKLIST.md`
**Description**: The 1.3.0 rehearsal recorded wheel sha256 `f85e6512…` / sdist `255d2c01…`. The
current artifacts in `code/dist/` hash to `67be362c…` / `02834d3c…`. Roughly 22 commits have
touched `code/src` since the CHANGELOG's 1.3.0 entry (2026-07-24), including the entire
core/theory_lib boundary refactor.
**Impact**: The checklist's pre-flight boxes are marked `[x]` but are no longer truthful. Any
release driven off that checklist would be publishing unrehearsed bytes.
**Recommended fix**: Re-run the rehearsal (fresh build, `twine check --strict`,
`check-wheel-contents`, wheel/sdist parity diff, fresh `nix flake check` on a quiet host) and
re-record the evidence before tagging.

### 2. `.github/workflows/README.md` documents a release process that does not exist

**File**: `.github/workflows/README.md`
**Description**: Still describes `PYPI_API_TOKEN` repository secrets (deliberately removed in
favour of OIDC Trusted Publishing), a Python 3.8/3.12 test matrix (actual: 3.10/3.11/3.12),
`cd Code` (wrong casing, previously fixed), a manual `twine upload` flow, and
`python code/run_update.py` — **a script that does not exist anywhere in the repository**.
**Impact**: This is the file someone would read when performing the release. Following it leads
to a failed or wrongly-credentialed publish.
**Recommended fix**: Rewrite to match the shipped five-job `release.yml`, or delete it and point
at `RELEASE_SETUP.md`.

### 3. PyPI OIDC trusted publisher and GitHub Environments are not configured

**File**: `specs/archive/125_release_engineering_and_pypi_rehearsal/PUBLISH-CHECKLIST.md` §2
**Description**: Every box in the one-time setup section is unchecked: the PyPI trusted publisher
for `benbrastmckie/ModelChecker` / workflow `release.yml` / environment `pypi`, and the `pypi`
and `testpypi` GitHub Environments. No `v1.3.0` tag exists (latest is `v1.2.12`).
**Impact**: **Hard blocker.** Pushing a tag today runs the pipeline up to `publish-pypi`, which
then fails on OIDC — after the test/build jobs have already burned. This is user-only work
(PyPI and GitHub web UI); no agent can perform it.
**Recommended fix**: Complete §2 before the first tag push.

## High Priority Issues

### 4. Nothing in the test suite ever runs the `model-checker` console script

**File**: `code/src/model_checker/builder/tests/test_package_loading.py:244`
**Description**: The one test that appears to invoke the console script patches
`subprocess.run` and then asserts against its own mock — it exercises no production code. CI
uses `python -m model_checker`, never the `[project.scripts]` entry point.
**Impact**: The single most user-visible artifact of the package — the `model-checker` command —
has zero real coverage. A broken entry point would ship undetected.
**Recommended fix**: Add tests that invoke the installed console script as a subprocess.

### 5. "Generate a project, then run it" is covered nowhere

**File**: `code/src/model_checker/builder/tests/` (multiple)
**Description**: Project generation is well covered *structurally* (file layout, markers,
imports), but no test generates a project and then executes it. `test_issue_73_fix.py:82`
explicitly patches `input` to `'n'` to skip the execution branch;
`integration/test_generated_projects.py:88` documents that generated projects "cannot be loaded
standalone".
**Impact**: This is the primary user journey (`model-checker` → scaffold → run). I verified it
manually here for all four theories; nothing verifies it automatically.
**Recommended fix**: Add a generate-then-execute test per registered theory.

### 6. `ParseFileFlags` has no tests at all

**File**: `code/src/model_checker/__main__.py:19`
**Description**: The argument-parsing class is never imported by any test. The only
argument-level coverage is five error-path cases in
`tests/integration/test_error_handling.py:15-73`, one of which
(`test_conflicting_flags`, :69) is an empty `pass` stub.
**Impact**: Flag parsing, short/long mapping, and flag-to-settings plumbing are unverified —
which is how issues 8 and 9 below survived.
**Recommended fix**: Direct unit tests for `ParseFileFlags.parse()` and the settings override path.

### 7. No general CI — the main suite runs on neither push nor PR

**File**: `.github/workflows/`
**Description**: Only two workflows exist: `release.yml` (tag-triggered only) and
`differential-tests.yml` (path-filtered to bimodal/oracle). Nothing runs `code/tests/` or the
in-package suite on ordinary pushes or pull requests.
**Impact**: Regressions land silently and are only discovered at tag time, when the cost of
finding them is highest. Already an open roadmap item ("Add `nix flake check` as a CI gate job").
**Recommended fix**: Add a push/PR workflow running both suites plus `nix flake check`.

### 8. `-p` silently does nothing

**File**: `code/src/model_checker/__main__.py:202`
**Description**: `_short_to_long` maps `c,d,e,l,m,n,q,s,i,v,u,z,a` but omits `p`. Because
`settings/settings.py:215` only applies an override when the long name is present in
`user_provided_flags`, `-p` never reaches the setting. `--print_constraints` works.
**Impact**: A documented flag silently no-ops. Users debugging constraints get no output and no
error.
**Recommended fix**: Add `'p': 'print_constraints'`; add a test asserting short and long forms
are equivalent for every flag.

### 9. `--load_theory` advertises only `bimodal` and validates nothing

**File**: `code/src/model_checker/__main__.py:77`
**Description**: `help='Load semantic theory: bimodal.'` is a hardcoded, stale string. The
registry reports four theories (`bimodal, logos, exclusion, imposition` — confirmed via
`registry.iter_theories()`). The argument also has no `choices=`, so invalid names fail late.
**Impact**: Users are never told from `--help` that logos, exclusion, and imposition exist.
**Recommended fix**: Generate the help text and `choices` from the registry, so it cannot drift
again.

## Medium Priority Issues

### 10. Wheel/sdist contents are never verified against their own allowlists

**File**: `code/pyproject.toml:72`, `code/MANIFEST.in`
**Description**: Both files carry long comments explaining that the `[tool.setuptools.package-data]`
allowlist and the `MANIFEST.in` allowlist must stay in sync — and nothing enforces it. No test
asserts that `oracle/`, `TODO.md`, `history/`, or `reports/` stay out, or that theory
`VERSION`/`docs/`/`notebooks/` stay in.
**Recommended fix**: Add a packaging-contract test that builds and inspects the artifacts.

### 11. `--save jupyter` is accepted, then silently discarded

**File**: `code/src/model_checker/output/config.py:64`
**Description**: `jupyter` is a valid argparse choice (`__main__.py:118`) but
`create_output_config` only maps `markdown`/`md` and `json`. `--save jupyter` therefore sets
`save_output=True` with an empty format list. The help text's "No args = all formats" is also
inaccurate — bare `--save` yields markdown+json only.
**Recommended fix**: Either implement the jupyter format or remove it from `choices`, and correct
the help text.

### 12. `--sequential`/`-q` is advertised but raises `NotImplementedError`

**File**: `code/src/model_checker/builder/module.py:139`
**Description**: The flag is documented in `--help` as interactive per-model saving, but the code
path raises unconditionally.
**Recommended fix**: Hide the flag until implemented, or fail with a clear user-facing message
rather than a traceback.

### 13. Dead `-j/--jupyter` pre-check block

**File**: `code/src/model_checker/__main__.py:252`
**Description**: `main()` scans `sys.argv` for `-j`/`--jupyter` and checks Jupyter dependencies,
but neither flag is registered on the parser — so argparse rejects them first and the block is
unreachable.
**Recommended fix**: Delete it, or register the flag.

### 14. `RELEASE_SETUP.md` has broken references and a stale matrix

**File**: `.github/RELEASE_SETUP.md:54,77,146`
**Description**: Line 54 describes a Python 3.8/3.12 matrix (actual: 3.10/3.11/3.12). Lines 77
and 146 point at `specs/125_release_engineering_and_pypi_rehearsal/`, which has since moved to
`specs/archive/125_…`.
**Recommended fix**: Correct the matrix and repoint the paths.

## Recommendations

1. **Do not tag until the rehearsal is redone and OIDC is configured.** Issues 1 and 3 are the
   two hard gates; everything else can follow the release if needed.
2. **Close the CLI verification gap before publishing, not after.** The CLI demonstrably works
   today (verified manually across four theories), but nothing would catch it breaking. Issues
   4, 5, and 6 together are the difference between "it worked when a human checked" and "it is
   known to work".
3. **Fix the cheap CLI defects first** (issues 8, 9, 11–13, 15) — they are small, user-visible,
   and should be in the published artifact rather than a follow-up.
4. **Treat the documentation issues as release-blocking**, not cosmetic. Issue 2 in particular
   would actively misdirect the person performing the release.
5. **Capture the NixOS venv verification recipe** so post-publish verification is repeatable
   despite the "no pip on NixOS" constraint.
