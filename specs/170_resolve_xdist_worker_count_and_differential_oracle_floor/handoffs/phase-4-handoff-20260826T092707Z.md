# Phase 4 Handoff: Peak-RSS-per-worker telemetry for the Python 3.12 job

**Status**: [COMPLETED]

## What happened

RED: wrote `code/tests/ci/test_worker_rss_sampler.py` first, driving the intended interface
(`parse_vm_rss_kb`, `read_vm_rss_kb`, `discover_descendant_pids`, `sample_once`, `PeakTracker`)
against synthetic `/proc/<pid>/status`-shaped fixtures under `tmp_path` -- fully hermetic, no
live-process dependency. Confirmed collection-time `FileNotFoundError` naming the missing
`.github/scripts/worker_rss_sample.py`.

GREEN: implemented the sampler `/proc`-only (no `psutil`, no new CI dependency; choice stated in
the module docstring). 20/20 unit tests pass. Discovery walks `PPid:` chains under a synthetic
proc root to find all descendants (any depth) of a root pid; `PeakTracker` tracks both per-pid
peak RSS (preserving a replaced worker's own peak rather than overwriting it -- the exact D
scenario) and aggregate (summed-across-currently-alive-workers) peak; `summary()` emits only
absolute KB figures plus the caller-supplied worker count, with no threshold/ceiling/ratio
anywhere (guarded by a dedicated test). Live-smoke-tested against a real `pytest -n 2` process:
discovered both worker pids and reported plausible nonzero peaks (55424 KB / 55208 KB).

Wired into `.github/workflows/tests.yml`'s existing "Run general test suite" step (not a separate
GH Actions step -- see the deviation note below), bash-conditional on
`${{ matrix.python-version }} = 3.12`. The parallel-pass pytest invocation is now backgrounded
unconditionally (for every Python version) with `wait "$PYTEST_PID"` as the actual gate; the
sampler only runs under 3.12 and its own failure is swallowed with `|| true`, so it can never
turn a green suite red. Verified this preserves gating semantics with two smoke tests: a passing
`pytest -n 2` run's exit 0 propagates through `wait`; a deliberately failing run's exit 1 also
propagates unchanged.

**Deviation, documented**: task item 3 named a "dedicated step." A literal separate GH Actions
step cannot observe a process backgrounded by an earlier step without either silently dropping
that earlier step's own pass/fail reporting, or making the "non-gating" telemetry step gating in
practice by moving the wait/exit-check into it. Inline placement within the same step avoids
both failure modes. A second, load-bearing reason forced backgrounding to be unconditional
(not per-branch): a first attempt duplicated the `pytest ... -n 4 ...` invocation line once per
`if`/`else` branch, which broke `test_workflow_parity.py::test_parallel_pass_marker_expression_matches`
and `test_worker_count_matches` ("expected exactly one parallel (`-n`) pass, found 2") -- exactly
the class of regression the plan's own Phase 4 Verification bullet warns is "a real finding, not
a test to adjust." Backgrounding the single literal invocation line unconditionally and only
conditionally invoking the sampler around it keeps the file to exactly one matched line.

Verification: `pytest code/tests/ci/test_worker_rss_sampler.py -v` 20/20 green.
`pytest code/tests/ci/ -q` 58/58 green, `test_workflow_parity.py` specifically confirmed still
passing (5/5). YAML validity confirmed via `python3 -c "import yaml; yaml.safe_load(...)"` (PyYAML
happens to be available in this local environment, even though the plan notes it is deliberately
absent from both CI toolchains -- this check is local-only convenience, not a CI-parity claim).
