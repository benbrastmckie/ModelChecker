# Phase 2 + 3 Handoff: Guard wiring (+ amendment) and test rewrites

- **Task**: 135 - Fix concurrent model building segfault
- **Phases**: 2 and 3 of 7
- **Status**: COMPLETED (both)

## What was done

### Phase 2 (guard wiring)

- `SemanticDefaults` (`models/semantic.py`) and `ModelDefaults` (`models/structure.py`) each
  gained `__init_subclass__` wrapping every concrete subclass `__init__` in `guard_construction`,
  plus their own `__init__` wrapped directly. `ModelConstraints.__init__`
  (`models/constraints.py`) wrapped directly.
- Class-level docstring paragraphs added stating the single-threaded-only contract and pointing
  at `models/concurrency.py`.
- Grep confirmed no production path constructs models off the main thread (only
  `output/progress/spinner.py:61` and `animated.py:158` use `threading.Thread`, neither
  constructs models).
- **Amendment, discovered during Phase 3's first single-run verification**: the rewritten
  `test_sequential_vs_concurrent` failed with `Z3Exception('Sort mismatch')` -- an outcome
  outside the contract (only `ok`/`ConcurrentConstructionError` are accepted). Root cause:
  `tests/utils/helpers.py::create_test_model()` calls `Syntax(...)` *before* the guarded
  `semantics_class(...)` call, and `Syntax.__init__` builds sentence-letter atoms via
  `syntactic/atoms.py::get_atom_sort()`, an unsynchronized check-then-set module-global cache
  (`_atom_sort`) that two threads can race on, each creating a distinct `AtomSort` object.
  Fixed by wrapping `Syntax.__init__` (`syntactic/syntax.py`) in the same `guard_construction`
  decorator -- consistent with production's sequential `Syntax(...)` -> `semantics_class(...)`
  call order (confirmed in `builder/example.py:173`, `builder/runner.py:79,198`).
- Full Phase 2 verification (deferred earlier while `oracle/run-oracle-suite.sh` ran, completed
  once it cleared):
  - `models/tests/unit/` -- 73 passed
  - `iterate/tests/` -- 220 passed (same-thread nesting intact)
  - `theory_lib/bimodal/tests/unit/` -- 258 passed, 1 failed
    (`test_example_cases[BM_CM_4-example_case9]`) -- **pre-existing, load-sensitive flake, not a
    regression**: passes in isolation (17.67s, within the documented 15-24s range for this
    example after a prior task widened its `max_time` to 30s), fails identically twice in a row
    only under full-suite CPU contention. The guard adds a cheap lock acquire/release, not
    solve-time overhead, so it cannot plausibly explain a 17.67s solve exceeding a 30s budget.
    Not fixed here (wall-clock budget tuning is Task 136's scope per this plan's Non-Goals).
  - `theory_lib/logos/tests/unit/` -- 40 passed
  - `syntactic/tests/` -- 71 passed (new coverage added by the amendment)
