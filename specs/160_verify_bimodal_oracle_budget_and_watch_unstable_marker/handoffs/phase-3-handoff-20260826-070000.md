## Deviation (recorded in the plan, per-item, per Pre-Edit Verification Gate)

Probing pytest's actual JUnit XML output for `_assert_scan_report`'s print()-then-assert shape
(`python3 -m pytest ... --junitxml=...` against a faithful local reproduction) showed
"disagreements=0" is NEVER present in `<failure>`'s message/text under pytest's default
`junit_logging` setting -- only a sibling `<system-out>` element carries it, and only when
`junit_logging` includes stdout (default: `no`). Without a fix, the gating branch's
"disagreements=0" check would be permanently unreachable in real CI, meaning this test could
never actually classify TIMING there -- exactly the failure mode this whole task exists to
prevent. Fixed by:
1. Extending `parse_junit()` to read a testcase's `<system-out>` sibling and fold it into
   `failure_text` for failed/error outcomes.
2. Adding `-o junit_logging=system-out` to `unstable-watch.yml`'s oracle-tree pytest invocation
   only (the code/ tree's BM_CM_1 signature needs no system-out).
3. Adding `TestParseJunitSystemOut` to the classifier test module, and correcting the Phase 1
   `FLOOR_MESSAGE` fixture (split into `FLOOR_ASSERTION_MESSAGE` + `FLOOR_MESSAGE`) to the
   realistic system-out-prefixed shape.

This touched two files the Phase 3 Scope Hypothesis did not anticipate
(`.github/workflows/unstable-watch.yml`, `code/tests/ci/test_unstable_watch_classifier.py`) --
recorded inline in the plan as a hypothesis miss, not absorbed silently.
