## Key Decisions Made

- `mcs_direct` enumerates ALL parts of `g(z)` per point (not just per-point maximal-compatible
  parts), since a general/interacting relation can make a jointly-maximal `rho` fail to decompose
  into independently-maximal per-point choices. Memoized on `(g, pi)` — without memoization the
  E3/E5 experiments (window size 3) do not finish inside a reasonable timeout.
- `thread()` checks EVERY pair `y < z` in the domain (matching `@def-task-coherent`'s own
  quantifier), not just consecutive pairs.
- `GeneralFrame.__init__` duplicates `base.Frame.__init__`'s state/world/possibility setup rather
  than calling `super().__init__()`, because the base constructor computes `histories` assuming
  the duration-uniform schema (no coherence filter at all); `GeneralFrame` needs the coherence
  filter in place before `histories` is built.

## What NOT to Try

- Do not run the direct-`mcs` engine over `frame_f3` (8 atoms, 256 states) without first reducing
  the time window or running detached with a bounded liveness check
  (`context/patterns/bounded-build-waiter.md`) — even `frame_small` (4 atoms) at window `{0,1,2}`
  needed the `_mcs_cache` memoization to finish inside two minutes; the 8-atom frame's `mcs_direct`
  candidate pool is `256^|X|`, which is intractable at `|X| >= 2` without a smarter (non-brute-force)
  per-point pruning strategy this phase did not build.
- Do not pipe the script's stdout through `| tail -N` when backgrounding a run: Python fully
  buffers stdout to a pipe, so a killed-by-timeout run loses ALL of its output. Redirect to a file
  with `python3 -u ... > file.log 2>&1 &` instead (as this phase's own runs do).
