# Phase 2 Handoff: GREEN — `/proc/<pid>/environ` worker-id tagging

**Status**: COMPLETED

## What was built

`.github/scripts/worker_rss_sample.py`:
- `parse_xdist_worker_id(environ_bytes) -> str | None` — exact-key match on
  `PYTEST_XDIST_WORKER` (never `startswith`, so `PYTEST_XDIST_WORKER_COUNT` cannot collide).
- `read_xdist_worker_id(proc_root, pid) -> str | None` — mirrors `read_vm_rss_kb`'s
  `(FileNotFoundError, ProcessLookupError, PermissionError) -> None` tolerance exactly.
- `PeakTracker.pid_to_worker: dict[int, str | None]`; `record()` gained an optional
  `worker_ids` parameter (default `None`, fully backward compatible with every existing call
  site).
- `summary()` gained `pid_to_worker` and `per_worker_id_peak_kb`.
- `_sample_worker_ids()` + `run()` updated to attach worker ids to every sample.
- Module docstring's "What the sampler records" paragraph updated to name the new fields and
  state attribution is best-effort. (The hypothesis-ledger paragraph is untouched — that is
  Phase 4's job.)

## Deviation from plan text (not from plan intent)

`sample_once()`'s return shape (`dict[int, int]`) is kept byte-identical rather than changed to
carry `(rss_kb, worker_id)` tuples, because several pre-existing/Phase-1 tests assert against the
old shape and Phase 1 forbids modifying existing tests. Worker-id attribution instead flows as a
parallel map (`_sample_worker_ids()`) threaded into `PeakTracker.record()`'s new `worker_ids`
kwarg inside `run()`. Same net effect (every sample gets both RSS and worker-id data), different
call shape. Recorded inline in the Phase 2 checklist per the pre-edit-gate contract.
