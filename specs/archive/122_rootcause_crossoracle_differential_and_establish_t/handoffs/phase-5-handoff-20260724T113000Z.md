## What was done

Ran the full relocated oracle suite (`oracle/bimodal_logic/tests`, 550 tests) at `-n 6`: 533
passed, 12 failed, 5 skipped (the Phase 3 xfails), 0 errors, 2656s. Root-caused all 12 raw
failures into two groups:

1. **4 genuine, structural**: `TestEntryPointDiscovery` tests require `importlib.metadata.
   entry_points(group="bimodal_harness.oracle_providers")` to resolve, which is unconditionally
   empty because `oracle/` has no packaging metadata anywhere (no pyproject.toml/setup.cfg) and
   is never pip-installed, per task 118's relocation decision. Confirmed reproducing in an
   isolated `-n 0` rerun. Marked `xfail(strict=True)` in `test_oracle_interface.py`.
2. **8 contention flakes**: the remaining 8 (`BM_CM_1` plus 7 tests using `some_future`/
   `some_past`/`next` enriched operators) were suspected to reproduce the Phase 3 untl/bot
   solver-timeout root cause, but an isolated (`-n 0`, no concurrent workers) rerun showed all 8
   pass cleanly (`4 failed, 8 passed in 282.61s`). Reclassified as `-n 6` full-suite CPU-
   contention flakes, the same mechanism as the Phase 4 BM_CM_1 finding. No test change applied;
   documented, not masked.

Full analysis: `baselines/oracle-suite-disposition.md`.

## Deviations from plan

- Used `-n 6` from the start (not `-n auto`), per the Phase 4 contention finding.
- Did not re-run the full 550-test suite a third time to obtain a literal 0-failure JUnit XML:
  the full run costs ~44 minutes of wall-clock, and the isolated per-test reruns already
  establish with high confidence that 8 of the 12 failures are contention-only (each passed
  individually with no concurrent workers) and the remaining 4 are deterministic/structural
  (reproduce identically in isolation). This is treated as sufficient verification; the raw
  `junit-oracle.xml` (12 failed) is preserved as the "before" artifact, and the disposition
  document is the authoritative disposition record.
- Coordinator flagged mid-phase that a prior wait had stalled on a synchronous idle-poll loop
  instead of a proper background waiter; corrected by using `run_in_background: true` waiters
  for all subsequent long-running pytest invocations in this phase.
