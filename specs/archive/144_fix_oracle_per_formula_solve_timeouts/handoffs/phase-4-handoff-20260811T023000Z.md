# Phase 4 Handoff: ForAllTime/ExistsTime Trigger Investigation (Dead End)

- **Task**: 144 - fix_oracle_per_formula_solve_timeouts

- **Status**: COMPLETED (gate executed since headroom was thin; no legal/safe trigger found;

## Gate Decision

The plan gates Phase 4 on whether any Phase 1 target formula still has `max(wall)` headroom below
2x its budget after Phases 2-3. Since both Phase 2 and Phase 3 were rejected, the Phase 1 baseline
numbers are still current: `and_box_next` sits at `max(wall)=60.37s` against a 60s budget (~1.0x
headroom), and inspecting the Phase 1 baseline's raw per-sub-formula data showed
`all_sat_task_relation_ternary`'s `next_A` leg actually **timed out** at seed 3
(`structure.timeout=True`, 180.47s wall against the 180000ms budget). Both are far below the 2x
threshold, so the gate required executing this phase rather than skipping it.

## What Was Tried

`is_valid_time(time_var)` is confirmed arithmetic (`z3.And(t > ..., t < ...)`), not pattern-eligible
as-is, matching the research report. Rather than assume `ForAllTime`/`ExistsTime`'s body is entirely
opaque, direct AST inspection of the actual `\next(B) = Until(B, bot)` translation (the operator all
three Phase 1 targets use) was performed by monkey-patching `ForAllTime`/`ExistsTime` in a scratch
script and walking the constructed `body` expression. This found that a genuine function-application
subterm mentioning the bound time variable (`Select(world_function(w), time_var)`, i.e.
`world_function(0)[time_var]`) IS syntactically present in the guard-time `ForAllTime`'s body for
this specific case.

A bounded, depth-limited AST-walking helper (`_find_body_time_pattern`) was implemented in
`core.py` to auto-detect such a subterm at `ForAllTime`-construction time -- strictly opt-in (falls
back to the original unpatterned form whenever no candidate is found), and deliberately simple (no
`MultiPattern`, no "best of several candidates" logic, given the demonstrated risk from Phase 2's
dead ends 7/8).

## Why It Was Rejected

Applying the discovered term as `patterns=[...]` to the actual guard-time `ForAllTime` call inside
`\next(B)`'s `Until`/`bot` translation produced a **hard Z3 construction-time error**:
`z3.z3types.Z3Exception: b'invalid pattern'`. This is a stronger negative than Phase 2's dead ends
(which were legal-but-harmful) -- Z3's pattern-legality rules are stricter than "syntactically
contains the bound variable inside a function application." The located subterm's specific shape
(from `bot`'s always-false self-inequality encoding, `Select(...) != Select(...)` with the identical
subexpression on both sides) is very likely rejected because it does not admit a well-founded
matching order, or a similar internal legality rule this task did not have budget to fully diagnose
within Phase 4's hard time-box.

Reliably finding a legal body-derived pattern in the general case (arbitrary operator arguments, not
only this task's atomic-argument benchmark) would require either a substantially more careful AST
walk with correctness rules beyond this task's scope, or restructuring `ForAllTime`/`ExistsTime`'s
API so callers supply an explicit trigger hint at construction time -- both are out of scope per the
plan's non-goal on broad `core.py`/`operators.py` refactoring beyond the named quantifier sites.

`ExistsTime` was separately analyzed (not implemented): for all three Phase 1 targets, the
`ExistsTime` call inside `\next(B)`'s translation is (or sits inside a top-level `And` with) the
outermost quantifier for that subformula, which Z3's own preprocessing skolemizes away before the
main search begins. A `patterns=` argument on a soon-to-be-skolemized `Exists` is inert regardless of
dead end 11's outcome, so no implementation effort was spent there, per the plan's explicit "if
inert, do not spend effort" guidance.

Both changes were reverted; the final `core.py` state is functionally identical to the Phase 1
baseline (confirmed by exact rlimit reproduction: seed-0 `and_box_next` rlimit=130120807).
