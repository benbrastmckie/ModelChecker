## Measurement (the plan requires a measured, not assumed, choice)

`/usr/bin/time` is unavailable on this host (NixOS); measured instead via
`resource.getrusage(RUSAGE_SELF)` deltas taken inside a Python harness that imports the sampler
module directly and calls `sampler.run()` against a real, locally-launched
`pytest tests/ src/model_checker -m "not packaging and not performance and not unstable and not
xdist_serial and not development" -n 4` (the actual gating parallel-pass command):

| `--interval` | sampler CPU (user+sys) | wall | CPU fraction of 1 core | samples |
|---|---|---|---|---|
| 0.25 | 6.134s | 96.207s | 6.375% | 361 |
| 0.5 | 2.749s | 83.782s | 3.28% | 163 |

0.25's overhead (6.375%) clears the plan's ~2% target by more than 3x, so per the plan's own
binary rule, **0.5 was chosen** (the designated fallback) rather than searching for an
in-between value. 0.5's own measured overhead (3.28%) is also above 2% on this shared local
host, but the plan's rule is a two-value choice, not an iterative search, and this host's
absolute numbers are not the dedicated `ubuntu-latest` CI runner's — recorded honestly as such,
carried into Phase 4's ledger rather than smoothed over.

Note: a subtlety in the measurement harness itself (Python's `subprocess.Popen` doesn't
auto-reap a background child the way bash's job control does, so an unreaped harness would spin
forever on `_process_alive()` seeing a zombie as alive) was worked around with a daemon reaper
thread in the throwaway measurement script — this does not affect `worker_rss_sample.py` itself,
which is invoked from bash in production exactly as `tests.yml` already does, and bash reaps its
own background jobs.
